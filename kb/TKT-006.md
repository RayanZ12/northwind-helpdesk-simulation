# TKT-006 — Need access to the Finance folder

| Field | Value |
|---|---|
| Category | Accounts and Authentication (service request) |
| Help topic | New User Account Request |
| Department | Support |
| Priority / SLA | Normal — P3 (24h, business hours) |
| Affected user / system | Ryan Thompson (Sales) — `\\FS01\Finance` (`C:\Shares\Departments\Finance`) |
| Resolved by | Tier 1, after written approval from the Finance data owner |

> **Naming note:** the ticket catalog names the requester "Julie Tremblay (Sales)", but no
> account by that name exists in the 45-user Active Directory set built in Project 1. As
> with TKT-005, the ticket was run against a real account from the same department,
> **Ryan Thompson** (`ryan.thompson`, Sales Coordinator), keeping the scenario and
> resolution path as written in the catalog.

## Symptom

> Hi, I need to get into the Finance shared folder for the quarterly report. Can you give
> me access please? Thanks.

Nothing is broken. This is an access request from a user **outside the department that owns
the data**. The request doesn't say who asked for the report, which files are needed,
whether read access is enough, or for how long.

**The correct answer to this ticket is a process, not a permission change.** A Tier 1
technician has the technical rights to add anyone to any group. Having the rights doesn't
mean they should. Finance data belongs to Finance, and only its owner decides who reads it.

## Diagnosis

1. **Check:** the requester's current group membership —
   **Why:** confirm what access Ryan already has before deciding what to add, and make sure
   the request isn't really a broken existing permission (which would be an incident, not a
   request) — **Result:** Ryan's only group is `GG_Sales`. His effective token contains no
   Finance group at all, so the "access denied" he would get today is correct behaviour.

   ```powershell
   # DC01
   Import-Module ActiveDirectory
   $dn = (Get-ADUser ryan.thompson).DistinguishedName
   (Get-ADObject -Identity $dn -Properties tokenGroups).tokenGroups |
       ForEach-Object { $_.Translate([System.Security.Principal.NTAccount]).Value } | Sort-Object

   # BUILTIN\Users
   # NORTHWIND\DL_Sales_Share_RW
   # NORTHWIND\Domain Users
   # NORTHWIND\GG_Sales
   ```

   `tokenGroups` is the fully expanded (nested) group list the DC puts into the user's
   Kerberos ticket. It is more reliable than `MemberOf`, which only shows direct
   memberships.

2. **Check:** how the Finance folder is secured, at share level and at NTFS level, on FS01 —
   **Why:** find the group that gives the *least* access the request needs, instead of
   picking a group from its name — **Result:** access is granted only through the AGDLP
   domain-local groups. `BUILTIN\Users` is removed and inheritance is disabled.
   `DL_Finance_Share_RO` (read-only) exists and is **empty**.

   ```powershell
   # FS01
   Get-SmbShareAccess -Name Finance
   # NORTHWIND\Domain Admins        Allow  Full
   # NORTHWIND\DL_Finance_Share_RW  Allow  Change
   # NORTHWIND\DL_Finance_Share_RO  Allow  Read

   (Get-Acl C:\Shares\Departments\Finance).Access |
       Select-Object IdentityReference, FileSystemRights, IsInherited
   # NT AUTHORITY\SYSTEM            FullControl                  False
   # BUILTIN\Administrators         FullControl                  False
   # NORTHWIND\Domain Admins        FullControl                  False
   # NORTHWIND\DL_Finance_Share_RW  Modify, Synchronize          False
   # NORTHWIND\DL_Finance_Share_RO  ReadAndExecute, Synchronize  False
   ```

   ```powershell
   # DC01
   Get-ADGroupMember GG_Finance           # ahmed.hassan, jennifer.lam, rajesh.patel, sarah.macdonald, wei.zhang
   Get-ADGroupMember DL_Finance_Share_RW  # GG_Finance
   Get-ADGroupMember DL_Finance_Share_RO  # (empty)
   ```

3. **Check:** who owns the data —
   **Why:** the approval has to come from the data owner. The requester's own manager and
   IT can't approve it — **Result:** **Ahmed Hassan, Finance Director** (`Title` attribute in
   AD, member of `GG_Finance`).

### Why not just add him to `GG_Finance`?

The catalog's resolution path says "grant via the appropriate global group". At first
glance the matching global group is `GG_Finance`. That would be wrong:

- `GG_Finance` is nested into `DL_Finance_Share_RW`, so it gives **Modify** (create,
  change, delete Finance files), not read.
- It would make a Sales employee a member of the Finance *role* group. Anything scoped to
  "Finance staff" in the future (another share, a GPO filter, an application role) would
  include him without anyone deciding that.

Global groups in this domain represent **who someone is** (their department). Domain-local
groups represent **what a resource allows**. A cross-department read request belongs on
the resource side.

## Resolution

1. **Request approval before any change.** An internal note on the ticket recorded that
   Tier 1 asked Ahmed Hassan (Finance Director) to approve. The request stated who is
   asking, why (quarterly report), the proposed access level (**read-only**) and the
   proposed duration (until the report is filed, reviewed at quarter end). The user was told the
   request was pending owner approval. Nothing was changed in AD at this stage.

2. **Approval received (simulated for the lab):** Ahmed Hassan approved **read-only**
   access for the quarterly report. His written approval was recorded on the ticket in an
   internal note. A verbal "my manager said it's fine" relayed by the requester isn't
   enough: the approval has to come from the data owner and be on file.

3. **Grant least privilege through the resource's read-only group:**

   ```powershell
   # DC01
   Add-ADGroupMember -Identity DL_Finance_Share_RO -Members ryan.thompson
   ```

   GUI equivalent: *Active Directory Users and Computers > NORTHWIND > Groups > Finance >
   DL_Finance_Share_RO > Properties > Members > Add… > ryan.thompson*.

   **Documented deviation from AGDLP:** strictly, a user should never be a direct member
   of a domain-local group. The strict version would be a new global group (for example
   `GG_Finance_Readers`) nested into `DL_Finance_Share_RO`. For a **single, approved,
   time-limited** exception, creating a new role group adds an AD object that says less
   than a direct, documented membership. It also falls outside the objects named in this
   ticket. If a second person outside Finance needs the same access, that's the signal to
   create the global group and move both memberships into it.

4. **User instruction:** group membership is added to the Kerberos ticket at logon, so
   Ryan has to **sign out and back in** (or lock and unlock after a reboot) before the
   Finance share opens. Otherwise he gets a false "it still doesn't work" follow-up.

## Root cause

Not a fault. A user outside the owning department asked for access to departmental data.
The existing permissions worked as designed. The only question was whether the data owner
approved an exception.

## Verification

Ryan's expanded token now includes the read-only Finance group and nothing that grants
write:

```powershell
# DC01
# BUILTIN\Users
# NORTHWIND\DL_Finance_Share_RO     <- new
# NORTHWIND\DL_Sales_Share_RW
# NORTHWIND\Domain Users
# NORTHWIND\GG_Sales

Get-ADGroupMember DL_Finance_Share_RW   # still only GG_Finance — no write path added
```

Effective NTFS access on `C:\Shares\Departments\Finance` was computed on FS01 with the
Windows Authz API (`AuthzAccessCheck`, the same engine behind *Properties > Security >
Advanced > Effective Access*). Each user's SID and `tokenGroups` from DC01 were used, so
no user password was needed. A Finance user and an unapproved Sales user were included as
controls:

```text
User           Read  Write  Delete  Rights
----           ----  -----  ------  ------
ryan.thompson  True  False  False   ReadAndExecute, Synchronize
wei.zhang      True  True   True    Modify, Synchronize
marco.rossi    False False  False   None
```

Ryan can read but not change or delete. Finance staff are unaffected. Another Sales user
who wasn't approved still has no access, which confirms the grant is scoped to one person
and not to Sales. At share level `DL_Finance_Share_RO` has **Read**, so the effective
access over `\\FS01\Finance` is read-only as well.

GUI equivalent for a manual check: *FS01 > C:\Shares\Departments\Finance > Properties >
Security > Advanced > Effective Access > Select a user: ryan.thompson > View effective
access*.

## Prevention

- **Access reviews:** a direct user member in a `DL_*` group is by definition an exception.
  A quarterly check such as
  `Get-ADGroupMember DL_Finance_Share_RO | Where-Object objectClass -eq 'user'`
  catches exceptions that outlived their reason. This one should be removed once the
  quarterly report is filed.
  (Windows Server's time-limited group membership would do this automatically. It needs
  the Privileged Access Management optional feature, which is irreversible once enabled
  and was deliberately not turned on in this lab.)
- **Request intake:** the help topic form for access requests should ask for the business
  reason, the access level needed and the data owner up front. That removes a round trip
  on every request like this one.
