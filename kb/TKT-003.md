# TKT-003 — Password expired and now I'm stuck

| Field | Value |
|---|---|
| Category | Accounts and Authentication |
| Help topic | Password Reset / Account Locked |
| Department | General Support |
| Priority / SLA | High — P2 (8h, business hours) |
| Affected user / system | Marco Rossi (Finance) |
| Resolved by | Tier 1 |

## Symptom

> It asked me to change my password when I logged in and I did, but now nothing works. It
> says the password doesn't meet requirements. What are the requirements?

The user successfully triggered a forced password change but chose a new password that
was rejected by domain policy. The generic client-side error doesn't state the actual
requirements, leaving the user stuck without knowing what to try next.

## Diagnosis

1. **Check:** `Get-ADDefaultDomainPasswordPolicy` — **Why:** get the authoritative policy
   values instead of guessing what the user's password might be missing — **Result:**
   `ComplexityEnabled=True`, `MinPasswordLength=12`, `PasswordHistoryCount=24`.
2. **Check:** `Get-ADUser marco.rossi -Properties PasswordExpired, pwdLastSet` —
   **Why:** confirm the account is genuinely mid forced-change, not locked or disabled —
   **Result:** `pwdLastSet=0`, confirming a pending forced change (matches the user's
   description).
3. **Check:** reproduced the failure directly with a deliberately weak test password —
   **Why:** confirm the exact rejection message the user would have seen, rather than
   assuming — **Result:** identical rejection.

```powershell
Import-Module ActiveDirectory
Get-ADDefaultDomainPasswordPolicy | Select-Object ComplexityEnabled, MinPasswordLength, PasswordHistoryCount

# ComplexityEnabled    : True
# MinPasswordLength    : 12
# PasswordHistoryCount : 24

$weak = ConvertTo-SecureString "password123" -AsPlainText -Force
Set-ADAccountPassword -Identity marco.rossi -NewPassword $weak -Reset

# Set-ADAccountPassword : The password does not meet the length, complexity,
# or history requirement of the domain.
```

## Resolution

```powershell
Set-ADAccountPassword -Identity marco.rossi -NewPassword <temp, compliant, generated at
    point of use, not logged> -Reset
Set-ADUser -Identity marco.rossi -ChangePasswordAtLogon $true
```

The forced-change flag was kept on so Marco sets his own password on next logon rather
than continuing to use a temp value known to IT.

The reply to the user translated the policy into plain language and gave a concrete,
easy-to-follow pattern (a short passphrase with a number and symbol) rather than just
repeating the technical requirement list.

## Root cause

The user's chosen replacement password did not satisfy the domain's complexity policy
(12+ characters, upper/lower/number/symbol, no reuse from the last 24 passwords). Windows'
own error message doesn't list the specific requirements, so the user had no way to
self-correct without contacting IT.

## Verification

```powershell
Get-ADUser marco.rossi -Properties LockedOut, pwdLastSet, PasswordExpired

# LockedOut       : False
# pwdLastSet      : 0
# PasswordExpired : True
```

Same verification approach as TKT-001: `pwdLastSet=0` and `PasswordExpired=True` confirm
the account is correctly waiting on the user to set their own password, without requiring
an interactive logon test with a temporary credential.

## Prevention

The underlying friction — Windows' generic complexity-rejection message not stating the
actual policy — is a recurring source of this exact ticket type. A short, plain-language
password-requirements note in the company intranet or the logon banner would let users
self-serve instead of opening a ticket. Noted as a candidate improvement, not implemented
here (out of scope for a single ticket).
